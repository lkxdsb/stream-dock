# 抖音本地工具多格式导出设计说明

## 目标
在当前本地工具基础上，把导出能力从：

- 音频：`m4a` / `mp3`
- 视频：`mp4`

扩展为：

- 音频：`m4a` / `mp3` / `wav` / `flac` / `aac` / `ogg` / `opus`
- 视频：`mp4` / `mkv` / `mov` / `webm`

第一阶段只解决“多格式稳定导出”，不扩大到批量任务、多平台、历史记录等方向。

## 设计原则

1. 保持现有使用方式不变，CLI 仍只保留 `link` / `outputPath` / `outputType` 三个核心参数。
2. 网页入口不改交互模型，只扩充输出格式下拉框。
3. 把“抓流”和“导出”分层，避免后续每加一种格式都继续堆 `if/else`。
4. 视频类输出优先保证“文件真实可播放”，不能再生成只有音频或只有视频的伪完整文件。
5. 优先复用源流，只有封装不兼容时再转码，避免无谓损耗和耗时。

## 当前问题
当前脚本已经能抓到：

- 独立音频流
- 独立视频流
- 视频页真实跳转地址

但输出层仍是面向 `m4a` / `mp3` / `mp4` 的定制逻辑，继续硬扩会带来两个问题：

1. 新格式越多，`materialize_output()` 会越来越难维护。
2. 不同容器的能力差异很大，不能再把“所有视频格式都当 mp4 改后缀”处理。

因此第一阶段的核心不是“多加几个 ffmpeg 命令”，而是先建立统一输出策略层。

## 核心方案

### 1. 引入输出格式注册表
把每种输出格式定义成一条明确策略，而不是继续写分支判断。

每个格式至少声明：

- `kind`：`audio` 或 `video`
- `extension`：输出后缀
- `needs_video_stream`
- `needs_audio_stream`
- `mode`：`copy` / `extract` / `mux` / `transcode`
- `ffmpeg_args_builder`：生成具体 ffmpeg 参数

这样后续再加格式时，只需新增注册项，不需要继续改主流程结构。

### 2. 统一中间素材模型
抓流阶段输出统一结构：

- `media_kind`
- `video_url`（可为空）
- `audio_url`（可为空）
- `media_url`（兼容现有流程）
- `title`
- `final_url`

下载阶段统一落地为临时文件：

- `source_video`
- `source_audio`

后续所有导出逻辑都只面向这两个本地素材文件，不再直接感知抓流细节。

### 3. 音频格式策略

#### `m4a`
- 有独立音频流时优先直接封装/复制
- 否则从视频中抽取音频
- 默认尽量避免重复编码

#### `mp3`
- 统一转码为 `libmp3lame`
- 保持当前行为不变

#### `wav`
- 输出无损 PCM
- 适合本地剪辑、转写、再次处理

#### `flac`
- 输出无损压缩音频
- 适合长期保存

#### `aac`
- 输出 AAC 音频文件
- 若源已是 AAC 且容器兼容，优先复制
- 否则转码为 AAC

#### `ogg`
- 第一阶段明确输出 Ogg Vorbis
- 避免和 Opus 容器策略混淆

#### `opus`
- 输出 `.opus`
- 使用 Opus 编码，优先面向高压缩率场景

### 4. 视频格式策略

#### `mp4`
- 若有独立视频流 + 独立音频流，先本地合并
- 若只有完整视频流，则直接复制或重封装
- 保持当前已修复行为

#### `mkv`
- 优先无损复用音视频流并封装到 MKV
- 作为“兼容性强、容器灵活”的视频输出

#### `mov`
- 优先复用现有 H.264/AAC 流并重封装
- 作为 Apple 生态更友好的输出形式

#### `webm`
- 不直接复制 H.264/AAC 到 WebM
- 第一阶段明确走转码：
  - 视频转 `libvpx-vp9`
  - 音频转 `libopus`
- 这是本阶段唯一明确默认重编码的视频格式，代价更高但行为最清晰

## 数据流

### CLI / 网页入口
用户仍只提供：

- `link`
- `outputPath`
- `outputType`

### 解析阶段
- 提取短链/分享文案里的真实 URL
- 获取媒体捕获结果
- 判断选中格式属于音频还是视频

### 下载阶段
- 如需视频，下载视频流到临时目录
- 如需音频，下载音频流到临时目录；如果没有独立音频流，则允许后续从视频抽取

### 导出阶段
- 根据 `outputType` 在注册表中查策略
- 执行以下之一：
  - 直接复制
  - 抽音频
  - 音视频合并
  - 转码
- 最终写入 `outputPath`

## 错误处理
需要明确区分这些错误：

1. 不支持的输出类型
2. 目标格式要求视频轨，但当前只拿到音频轨
3. 目标格式要求音频轨，但既没有独立音频也无法从视频抽取
4. ffmpeg 不存在或执行失败
5. WebM 转码失败
6. 多流合并失败

用户可见层面要给出可理解提示，例如：

- `Only audio stream found; cannot export a real mp4 video`
- `Selected format webm requires transcoding but ffmpeg failed`

## 网页改动范围
第一阶段网页只做最小变更：

- 扩充格式下拉框
- 保持现有提交接口不变
- 失败时原样显示后端日志

本阶段不新增：

- 分组选项卡
- 码率/采样率控制
- 自定义 ffmpeg 参数

## 兼容性约束
为了保证第一阶段收敛，明确采用以下固定策略：

1. `ogg` 固定为 Vorbis，不做 `ogg+opus` 双路线。
2. `opus` 固定输出 `.opus`。
3. `webm` 固定转码，不做“有条件 copy”。
4. `mov/mkv/mp4` 优先复用流，只有不兼容时才转码。
5. 先不开放用户自定义编码参数。

这样可以减少第一阶段的分叉复杂度。

## 测试策略

### 单元测试
至少新增三类测试：

1. 输出格式注册表能正确识别音频/视频类型。
2. 同时存在音视频流时，视频导出优先使用视频流并保留音频流信息。
3. 视频+音频临时文件合并后，输出文件实际包含两条轨道。

### 回归测试
对真实抖音样本验证：

1. `wav / flac / aac / ogg / opus` 能正常产出音频文件。
2. `mkv / mov / webm` 能正常产出视频文件。
3. 已知“分离视频轨 + 分离音轨”样本导出的 `mp4 / mkv / mov / webm` 中，至少 `mp4 / mkv / mov` 明确含音频轨和视频轨；`webm` 验证转码后仍含双轨。
4. 只拿到音频流的样本在选择视频格式时会直接失败，而不是生成假文件。

## 第一阶段范围

### 包含
- 输出格式注册表
- `wav / flac / aac / ogg / opus / mkv / mov / webm` 支持
- CLI 下拉参数扩展
- 网页下拉框扩展
- 必要测试补齐

### 不包含
- 批量任务
- 下载历史
- 打开输出目录按钮
- 多平台扩展
- 封面图 / 元信息 / 字幕导出
- 编码参数高级设置

## 结论
第一阶段不是把格式“硬堆满”，而是把当前本地工具升级成一个更稳的多格式导出内核：

- 入口不变
- 使用方式不变
- 输出格式显著增加
- 内部结构更适合后续继续做大

这样后面你要继续做批量任务、历史记录、更多平台时，底层导出能力不会成为阻碍。
