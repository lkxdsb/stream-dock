# 国产主流视频平台本地解析工具多平台架构设计说明

## 目标
把当前仅面向抖音的本地解析工具，升级成一个可扩展的多平台本地工具框架。

第一阶段范围明确限定为：

- 平台：抖音 / 快手 / B站
- 内容类型：普通视频
- 入口方式：统一入口自动识别平台
- 成功标准：尽量保留原始质量与音视频结构

当前目标不是立刻覆盖所有平台和所有内容形态，而是先把“多平台框架”搭稳，并在这个框架上逐步接入平台适配器。

## 为什么要做多平台架构
当前项目已经具备：

- 本地网页入口
- 单链接解析流程
- 音频/视频多格式导出
- 抖音平台的实际可用链路

如果后续继续在现有单脚本逻辑上直接叠加快手、B站、小红书等平台，会很快遇到这些问题：

1. 平台识别、抓流、下载、导出逻辑耦合在一起。
2. 某个平台调整页面结构时，容易波及整个工具。
3. 后续要加清晰度选择、批量任务、失败重试时，代码边界会越来越混乱。
4. 网页入口和命令行入口都会被迫写越来越多的平台特判。

因此，必须尽早把“平台解析”和“统一下载导出”分开。

## 架构路线选择

### 方案一：单脚本继续堆平台分支
- 在现有主脚本中继续增加 `if douyin` / `if kuaishou` / `if bilibili`
- 优点：短期开发最快
- 缺点：很快失控，不适合持续扩平台

### 方案二：平台适配器 + 统一媒体模型 + 统一导出内核
- 每个平台只负责识别链接、归一化链接、提取媒体信息
- 所有平台统一输出同一种媒体结果模型
- 下载、合并、转码、导出全部复用一套内核
- 优点：边界清晰，最适合长期做大
- 这是本设计采用的方案

### 方案三：平台适配器 + 完整任务流水线系统
- 在方案二基础上再提前引入任务历史、队列、状态机、失败重试等能力
- 优点：最适合未来大型本地工具
- 缺点：对当前阶段偏重，容易过度设计

## 第一阶段范围

### 包含
- 统一入口自动识别平台
- 抖音 / 快手 / B站三个平台适配器骨架
- 仅支持普通视频解析
- 统一媒体模型
- 统一下载与导出内核复用
- 现有本地网页入口继续可用

### 不包含
- 图文帖子
- 直播 / 直播回放
- 合集 / 剧集 / 番剧 / 课程
- 批量任务
- 任务历史
- 清晰度手选
- 多平台统一登录态中心
- 元数据深度抓取

## 总体架构
采用四层结构：

### 1. 统一入口层
负责：
- 接收分享文案或链接
- 接收输出目录和输出格式
- 调用平台识别逻辑
- 触发统一解析流水线

统一入口层不直接处理平台差异。

### 2. 平台适配器层
每个平台一个适配器，例如：
- `DouyinAdapter`
- `KuaishouAdapter`
- `BilibiliAdapter`

适配器只负责：
- 判断自己是否能处理当前链接
- 链接归一化
- 页面/请求/播放器链路观察
- 提取音频流、视频流、标题、封面等信息
- 输出统一媒体结果

适配器不负责：
- 最终格式导出
- 音视频合并策略
- 页面 UI 逻辑

### 3. 统一媒体模型层
所有平台最终都转换成统一结果模型，使下载器、导出器、网页入口不需要关心平台细节。

### 4. 统一下载 / 导出内核层
负责：
- 下载视频流与音频流
- 合并音视频
- 输出音频和视频格式
- 复用现有多格式导出能力

## 模块职责

### `app.py`
负责：
- 本地网页入口
- 参数接收与校验
- 调用统一 pipeline
- 返回结果给前端

不负责：
- 平台适配细节
- 导出实现细节

### `fetchers/models.py`
负责：
- 定义统一数据结构
- 作为平台适配器和导出层之间的公共协议

### `fetchers/adapters/base.py`
负责：
- 定义平台适配器基类接口
- 统一约束每个平台适配器的实现边界

### `fetchers/adapters/douyin.py`
负责抖音平台普通视频解析。

### `fetchers/adapters/kuaishou.py`
负责快手平台普通视频解析。

### `fetchers/adapters/bilibili.py`
负责 B站普通视频解析。

### `fetchers/registry.py`
负责：
- 注册平台适配器
- 根据链接自动选择适配器

### `fetchers/pipeline.py`
负责：
- 调用适配器
- 获取统一媒体结果
- 选择默认视频流与音频流
- 调用下载器与导出器
- 返回最终执行结果

### `fetchers/downloader.py`
负责：
- 下载视频流和音频流
- 管理临时文件

不负责：
- 平台判断
- 转码策略

### `fetchers/exporters.py`
负责：
- 合并音视频
- 转封装
- 转码
- 输出多格式文件

它直接承接当前已经实现的多格式导出能力。

## 平台适配器接口设计
每个平台适配器至少实现以下统一接口：

```python
class BasePlatformAdapter:
    platform_name: str

    def can_handle(self, raw_link: str) -> bool:
        ...

    def normalize_link(self, raw_link: str) -> str:
        ...

    def fetch_media(self, normalized_link: str) -> MediaFetchResult:
        ...
```

### `can_handle`
负责判断链接是否属于本平台，例如：
- 抖音：`douyin.com` / `v.douyin.com`
- 快手：`kuaishou.com` / `v.kuaishou.com`
- B站：`bilibili.com` / `b23.tv`

### `normalize_link`
负责：
- 从整段分享文案中提取 URL
- 展开短链
- 去掉无关参数
- 规范成适配器内部使用的标准链接

### `fetch_media`
负责：
- 打开页面或读取必要请求
- 识别媒体流
- 提取标题、作者、封面、流信息
- 返回统一结果模型

## 统一媒体模型设计
第一阶段统一定义四类核心模型。

### 1. `MediaStream`
表示一条可下载流：
- `url`
- `stream_type`（`video` / `audio`）
- `container`
- `codec`
- `width`
- `height`
- `bitrate`
- `filesize`
- `quality_label`

### 2. `MediaFetchResult`
表示平台适配器的完整输出：
- `platform`
- `content_type`
- `title`
- `source_url`
- `final_url`
- `cover_url`
- `author`
- `video_streams`
- `audio_streams`
- `preferred_video`
- `preferred_audio`
- `metadata`

### 3. `ExportRequest`
表示用户的导出意图：
- `output_path`
- `output_type`

第一阶段先不加入清晰度字段。

### 4. `ResolvedMediaSelection`
表示解析阶段最终选中的一组流：
- `video_stream`
- `audio_stream`
- `title`
- `output_type`

这样可以把“候选结果”和“最终下载选择”分开。

## 数据流

### Step 1：统一入口接收请求
输入：
- 分享文案或链接
- `outputPath`
- `outputType`

### Step 2：平台识别
由 `registry.py` 在适配器列表中找到能处理该链接的平台适配器。

### Step 3：平台适配器提取媒体结果
适配器返回 `MediaFetchResult`。

### Step 4：默认流选择
由 `pipeline.py` 从 `MediaFetchResult` 中选择一组默认：
- 默认视频流
- 默认音频流

此阶段目标不是开放清晰度选择，而是尽量保持原始质量与音视频结构。

### Step 5：下载和导出
- `downloader.py` 下载媒体流
- `exporters.py` 统一导出到目标格式

### Step 6：返回结果
统一返回：
- 解析平台
- 标题
- 输出文件路径
- 执行日志
- 错误信息（如果失败）

## 平台策略边界

### 抖音
复用当前已有能力，作为第一阶段的基准平台。

### 快手
第一阶段仅目标为：
- 普通公开视频
- 单视频页
- 尽量保留原始音视频结构

### B站
第一阶段仅目标为：
- 普通视频页
- 不覆盖番剧、课程、合集
- 尽量保留音视频结构

## 错误处理设计
错误应尽量分成两类：

### 平台层错误
例如：
- 链接不属于已支持平台
- 平台页面打开失败
- 平台未提取到媒体流

### 导出层错误
例如：
- 只拿到音频流却请求视频格式
- ffmpeg 转码失败
- 音视频合并失败
- 目标格式不支持

这样可以帮助后续在 UI 里更清楚地区分“平台问题”还是“导出问题”。

## 第一版开发顺序

### Phase 1：架构迁移
先把当前抖音链路迁移进新结构：
- `models.py`
- `registry.py`
- `pipeline.py`
- `adapters/douyin.py`
- `downloader.py`
- `exporters.py`

目标是把当前单脚本项目平移成多平台框架项目。

### Phase 2：抖音适配器稳定
验证：
- 新结构下抖音仍可用
- 当前多格式导出仍可用
- 网页入口不回归

### Phase 3：接入快手
新增 `adapters/kuaishou.py`，只做普通视频。

### Phase 4：接入 B站
新增 `adapters/bilibili.py`，只做普通视频。

### Phase 5：网页体验优化
最后再补：
- 平台识别显示
- 更清晰的错误提示
- 更稳定的结果展示

## 为什么这样分阶段
这种顺序的核心价值是：

1. 先搭稳定骨架，而不是先追求多平台数量。
2. 每新增一个平台，都复用前面的统一能力。
3. 任一平台失败时，问题能被隔离在对应适配器中。
4. 为后续清晰度选择、批量任务、历史记录预留明确接口。

## 后续扩展方向
当第一阶段稳定后，后续可以继续向下扩：

- 清晰度选择
- 图文内容解析
- 批量任务
- 任务历史
- 失败重试
- 更多平台（小红书 / 微博 / 视频号）

但这些都不应进入当前第一阶段范围。

## 结论
第一阶段多平台版的正确目标不是“做一个永不失效的全平台万能解析器”，而是：

- 做出一个统一入口
- 自动识别抖音 / 快手 / B站
- 仅支持普通视频
- 尽量保留原始质量和音视频结构
- 构建一个可长期迭代的适配器框架

这会让项目从“单平台脚本工具”升级为“多平台本地解析框架”，并且为后续继续做大打下真正稳定的基础。
