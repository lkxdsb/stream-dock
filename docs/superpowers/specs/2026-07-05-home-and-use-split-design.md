# StreamDock 首页展示页与在线使用页拆分设计

## 背景

当前前端页面同时承担了两种职责：

1. 首页品牌展示
2. 真实解析工具使用

这导致模板、样式、脚本都堆在同一组文件中，后续继续优化首页视觉、扩展新页面或维护工具逻辑时，修改边界不清晰，容易互相影响。

用户希望把当前首页改造成纯展示页，把真实工具能力迁移到独立的“在线使用”页面中，同时把前端按职责拆分为可维护的模块结构。

---

## 目标

本次改造完成后，前端需要满足以下目标：

1. `/` 只作为展示首页，不再承载真实解析功能
2. `/use` 承载真实解析工具能力
3. 顶部导航在两个页面中保持一致且位置不变
4. 首页右侧工具卡片改为演示型动态面板
5. 当前真实运行日志迁移到在线使用页
6. 当前前端代码不再集中堆在单一模板、单一样式文件、单一脚本文件中

---

## 范围

### 本次纳入范围

- 新增独立页面路由：
  - `/`
  - `/use`
- 抽取共享导航壳层
- 首页展示页改造
- 在线使用页迁移
- 前端模板、样式、脚本按职责拆分
- 首页 hero 区与下方内容区之间的过渡留白压缩

### 本次不纳入范围

- 更换前端框架
- 重做工具页视觉语言
- 重构后端接口
- 解析能力逻辑升级
- 新增复杂动画系统

---

## 用户体验设计

### 1. 首页 `/`

首页保留当前视觉气质与整体排版结构，但职责改变为“品牌展示 + 使用演示”。

#### 首页保留内容

- 顶部品牌与导航
- 左侧标题文案
- 平台节点与连线背景
- 右侧大面板的视觉位置和整体气质

#### 首页调整内容

- 删除导航中的“使用指南”
- 新增导航项“在线使用”
- 右侧大面板不再是真实表单
- 右侧大面板改为“演示型动态窗口”

#### 演示型动态窗口行为

该窗口只做演示，不发起真实请求。它展示一段简短的自动化使用过程，例如：

1. 自动填入一段示例链接
2. “开始解析”按钮出现交互态
3. 面板进入短暂处理中状态
4. 出现“解析成功 / 已完成 / 可导出”之类的结果态

演示应短、平滑、可循环，但不能喧宾夺主，也不能造成视觉噪音。

#### 首页留白调整

当前导航下方到 hero 主体之间的上部过渡区域偏高，导致页面节奏略松。需要缩短这一段垂直空间，使 hero 更自然地衔接导航与下方内容区域。

---

### 2. 在线使用页 `/use`

在线使用页承接当前真实工具页面能力，优先保持现有工具布局逻辑不变，避免本次改造把“页面分层问题”扩展成“产品工具重设计问题”。

#### 在线使用页保留内容

- 左侧状态菜单（解析 / 下载中 / 已完成 / 设置）
- 右侧主解析区域
- 链接输入
- 输出格式
- 清晰度识别与选择
- 保存路径
- B站 Cookie 输入
- 最近解析
- 解析结果
- 运行日志

#### 在线使用页调整内容

- 原本首页中的真实运行日志迁移到 `/use`
- 页面结构与视觉分区更清晰，但不重新发明布局
- 工具逻辑继续使用现有 `/api/probe` 与 `/api/fetch`

---

## 导航设计

两个页面共用同一套顶部导航。

### 导航项

- 产品
- 支持平台
- 在线使用
- 更新日志

### 行为原则

- `/` 与 `/use` 页面导航视觉保持一致
- 页面切换时，导航不闪烁、不换样式、不改位置
- 当前页面高亮状态需要准确反映

### 跳转规则

- 在首页中：
  - `产品 / 支持平台 / 更新日志` 可继续作为锚点导航或首页区块跳转
  - `在线使用` 跳转到 `/use`
- 在在线使用页中：
  - `在线使用` 高亮
  - 其他项可跳回首页对应区块，或跳回首页顶部再滚动到目标区域

## 前端架构设计

本次重点是把“共享壳层、页面、功能逻辑”拆开。

### 模板层

#### `templates/base.html`

职责：

- 公共 `<head>`
- 全局资源引入骨架
- 顶部导航
- 页面内容插槽

#### `templates/home.html`

职责：

- 首页 hero
- 首页展示区块
- 动态演示面板

#### `templates/use.html`

职责：

- 在线使用页工具布局
- 在线使用页功能容器

---

### 样式层

建议拆分为：

#### `static/css/base.css`

职责：

- CSS 变量
- reset
- 字体
- 通用布局基础

#### `static/css/header.css`

职责：

- 顶部导航栏
- 品牌区
- 导航项与按钮

#### `static/css/components.css`

职责：

- 通用按钮
- 通用输入框
- 通用卡片
- 状态块

#### `static/css/home.css`

职责：

- 首页 hero
- 背景结构
- 动态演示面板
- 留白控制

#### `static/css/use.css`

职责：

- 在线使用页布局
- 左右栏结构
- 工具区域布局

#### 可选：`static/css/logs.css`

职责：

- 日志区
- 最近解析
- 结果块样式

---

### 脚本层

建议拆分为：

#### `static/js/main.js`

职责：

- 全局初始化
- 通用辅助方法
- 导航高亮与跳转辅助
- 通用 toast

#### `static/js/home-demo.js`

职责：

- 首页动态演示面板逻辑
- 示例链接输入动画
- 处理中 / 成功态演示

#### `static/js/use-form.js`

职责：

- 在线使用页表单提交
- `/api/fetch` 调用

#### `static/js/use-quality.js`

职责：

- `/api/probe` 调用
- 清晰度探测
- 清晰度下拉渲染

#### `static/js/use-logs.js`

职责：

- 日志输出
- 状态文案更新

#### `static/js/use-result.js`

职责：

- 结果展示
- 最近解析展示

## 后端路由设计

需要在 `app.py` 中扩展页面路由：

- `GET /` → `home.html`
- `GET /use` → `use.html`

以下接口继续保持不变：

- `POST /api/probe`
- `POST /api/fetch`

这样可以把本次改造严格限制在“页面结构重组”，不影响当前后端解析链路。

---

## 状态与职责边界

### 首页演示逻辑

- 不访问真实解析接口
- 不污染真实日志
- 不依赖真实 probe 结果
- 只负责可视化演示“产品如何使用”

### 在线使用逻辑

- 负责真实业务交互
- 挂接现有 API
- 维护真实日志、状态、最近解析结果

### 关键边界原则

首页与在线使用页之间不共享“运行时任务状态”，只共享导航与基础视觉壳层。

---

## 兼容与迁移策略

本次改造应优先采取“迁移 + 拆分”的策略，而不是“先全部推倒重写”。

### 推荐迁移顺序

1. 先抽取共享模板与共享导航
2. 再把当前首页结构拆分到 `home.html`
3. 再把真实工具区迁移到 `use.html`
4. 最后拆 `style.css` 与 `app.js`

这样做可以在任何阶段都保持页面可运行，降低一次性大改风险。

---

## 验收标准

本次改造完成后，应满足以下验收项：

### 页面与路由

- 访问 `/` 显示展示首页
- 访问 `/use` 显示在线使用页
- 顶部导航在两个页面中保持一致

### 首页

- 首页右侧不再是真实输入表单
- 首页右侧展示自动演示流程
- 首页不再显示真实运行日志
- 首页导航下方过渡留白明显缩短

### 在线使用页

- 在线使用页保留现有解析能力
- 真实日志显示在在线使用页
- 真实最近解析显示在在线使用页
- probe / fetch 行为保持可用

### 代码结构

- 模板不再只剩一个 `index.html`
- 样式不再只集中在一个 `style.css`
- 工具逻辑不再只集中在一个 `app.js`

---

## 风险与控制

### 风险 1：迁移时工具页功能失效

控制方式：

- 在线使用页迁移时优先保留 DOM 结构关键 id
- 先迁移，再拆脚本逻辑

### 风险 2：首页展示与工具页逻辑耦合

控制方式：

- 首页演示脚本完全独立
- 不复用真实接口请求流程

### 风险 3：CSS 拆分后样式错位

控制方式：

- 先按页面与组件分层
- 保持类名稳定
- 每完成一层拆分即做页面验证

---

## 结论

本次前端改造的核心不是换视觉，而是建立一个可持续扩展的结构：

- 首页负责展示
- `/use` 负责真实功能
- 导航共享
- 页面职责清晰
- CSS / JS / 模板按模块维护

这会为后续继续做产品页、工具页和平台扩展提供稳定基础。
